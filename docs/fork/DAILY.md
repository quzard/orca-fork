# Daily upstream sync and Mac publish

`develop` is the integration branch and the repo's default branch. It is kept apart from upstream's `main` by name. Upstream is merged in, never rebased, so `develop` only moves forward and is never force-pushed. `fork/base` stays as an alias of the commit that became the integration branch and is not moved by these jobs. `fork/base-upstream` stays the last upstream commit a human pushed there.

GitHub Actions on this fork stay disabled. Neither job calls `workflow_dispatch` or deletes `.github/workflows`. A later upstream merge would restore deleted workflow files, and turning Actions on would run them.

## Cloud agent: merge and checks

Run on a fresh Linux checkout with Node 24 and pnpm 12.14.0. No git identity setup is needed: the script sets `GIT_AUTHOR_*` / `GIT_COMMITTER_*` to `quzard <30899719+quzard@users.noreply.github.com>` for its own merge, pin, audit-table and conflict commits.

```bash
bash fork/scripts/daily-sync.sh
```

The script stops unless `origin` is `quzard/orca-fork`. It fetches `upstream` (`https://github.com/stablyai/orca.git`, added when missing) and `origin/develop`, turns on `rerere`, checks out `origin/develop`, and merges `upstream/main` into it with `git merge --no-ff` (message `Merge upstream main through <sha> (<n> commits)`). It then points the local `fork/base-upstream` ref at `upstream/main` and runs `node fork/scripts/sync-skills-source-commit.mjs`; when `src/fork/skills-source-commit.ts` changed it commits `fix(fork): pin skill installs to the upstream base`, and any other change the pin script leaves fails the run. That local ref is what the pin script reads first. The job does not push `fork/base-upstream`.

If the localization runtime catalog verify (`pnpm run verify:localization-runtime-catalog`) fails after a merge, run `pnpm sync:localization-runtime-catalog` manually, review the regenerated `src/renderer/src/i18n/en-runtime-required.json`, and commit it on the attempt branch.

On a clean merge and green checks it pushes `develop` with a plain, non-force push. The push is a fast-forward; if someone else moved `develop` in the meantime, GitHub rejects it and nothing is overwritten. The push updates that branch ref only. It does not push tags or any other branch. Exit code is 0. The summary lines are `daily-sync: OK`, `upstream:`, and `develop:`. When nothing changed, `develop:` says `unchanged` and nothing is pushed.

Checks, in order, each reported by name when it fails:

1. `company-info`: `fork/scripts/verify/check-no-internal-refs.sh`, which ends with the commit identity check on `HEAD`.
2. `install`: `pnpm install --frozen-lockfile`.
3. `audit table`: `python3 fork/scripts/generate-audit.py`. When `docs/fork/AUDIT.md` changed, the job commits `docs(fork): regenerate the audit table`, so a moved upstream base or a stale table from a PR is fixed here.
4. `lint`: `pnpm exec oxlint`.
5. `pnpm run generate:rpc-params-catalog` (committed when it changes; the merge keeps the fork's copy through `merge=ours`), then `pnpm run verify:rpc-params-catalog`, `verify:bundled-skill-guides`, `verify:skill-bundle-manifest`, `verify:localization-runtime-catalog`.
6. `fork tests`: `node config/scripts/run-vitest.mjs run --config config/vitest.config.ts --maxWorkers=2 src/fork src/shared/fork-hooks`, which include the audit-table and daily-sync tests.
7. `typecheck`: `pnpm tc`.
8. The host Linux orcad slot: `pnpm build:orcad-prebuilds`, `--require-slots <slot>`, `--smoke`; `pnpm install --frozen-lockfile --dir mobile`; `pnpm build:mobile-web`; `node config/scripts/build-orcad-template.mjs --targets <slot>`, and a check that the manifest lists it. The host slot must be a Linux one. Set `ORCA_SYNC_DOCKER_SLOTS=1` to also run `fork/scripts/build-orcad-linux-prebuilds.sh` and stage `linux-x64-glibc,linux-arm64-glibc`. The home Mac package still builds those slots.

The job does not run the full `pnpm lint` (upstream's ratchet checks, `check:max-lines-ratchet` among them) or the full `pnpm test`. Run `pnpm lint` by hand after a merge that touched the hook files: on the fork it is expected to fail only where upstream `main` itself fails (see [SYNC.md](./SYNC.md) for the fork block in `config/max-lines-baseline.txt`).

On a merge conflict, or when a check fails after new commits exist, the script does not update `origin/develop`. It pushes the attempt to `sync/upstream-YYYYMMDD` (`ORCA_SYNC_TZ`, default UTC) with a plain push; if that branch already exists, it uses `-2`, `-3`, … instead, so an earlier manual resolution is never overwritten. An existing `sync/upstream-YYYYMMDD[-n]` branch that already holds the same attempt is reused and not pushed again. That is the same commit, or a branch whose commits from `origin/develop` match this attempt one for one: same count, same tree at each step, and the same upstream merge parent. A re-run after a conflict or a failed check makes new merge and pin commit SHAs, and still matches. A branch with any extra commit on top, such as a manual fix, never matches, even when its tree is unchanged, so the next run uses a new `-n`. A rejected `develop` push (someone moved it during the run) is reported the same way and parks the merge on an attempt branch. A conflict commit is a two-parent merge commit (`develop` and the upstream sha) whose tree contains every conflict marker. Exit code is non-zero. The summary names the reason, the untouched `develop` sha, and the attempt branch. Resolve that branch and open a PR against `develop`; merge it with a merge commit or fast-forward, never with rebase or squash, so the upstream parent is kept.

A dirty worktree, or a check failure when `HEAD` is still `origin/develop`, exits non-zero and pushes nothing.

Before each push (the attempt branch and `develop`) the script runs `fork/scripts/verify/check-commit-identity.sh`: every commit in `git rev-list <ref> ^upstream/main ^<floor>`, merge commits included, must have author and committer exactly `quzard <30899719+quzard@users.noreply.github.com>`. The one exception is a merge commit (2+ parents) made on github.com or by `gh pr merge`: author exactly quzard and committer exactly `GitHub <noreply@github.com>` passes; non-merge commits and any other committer still fail. A failure lists the offending SHAs, exits non-zero and pushes nothing, not even an attempt branch. A missing `upstream/main` ref fails the same way. The floor `8fd7c96acc934cb25e41b5da17f1743e88219bbe` (develop's `8fd7c96acc`) is fixed in the script and read from no file, so no commit can move it past itself or an earlier bad commit (the old `fork/scripts/verify/identity-baseline`, read from the checked ref's tree, allowed exactly that and is deleted). A floor missing from the repository, or not an ancestor of the ref, fails too. Commits up to the floor are public history checked when the check was added (no personal email; 20 of them are by `Cursor Agent <cursoragent@cursor.com>` and cannot be rewritten). Never change the floor. `check-no-internal-refs.sh` runs the same identity check after its content scan. `fork/push_github.sh` runs it before pushing, and `mac-auto-update.sh` runs it on the commit it is about to publish after `fork/scripts/verify/fetch-upstream-main.sh` refreshes `upstream/main` (the `upstream` remote, else the same URL this script adds); a failed fetch means no push and no publish. The fetch times out after `ORCA_UPSTREAM_FETCH_TIMEOUT` seconds (default 600): it is killed (TERM, then KILL after 5s, with its helpers) and the script exits non-zero, which callers treat as a failed fetch. It needs no GNU `timeout` and runs on macOS bash 3.2; git's `http.lowSpeedLimit`/`http.lowSpeedTime` also abort a transfer stalled for 120s. The fetch runs in its own process group (`set -m` job control; macOS has no `setsid`), so when launchd stops the job (unload, logout, shutdown) and signals the script's group, the fetch and its helpers are not in it. The script therefore traps TERM, INT and HUP: it stops the watchdog, then the fetch's whole group, and exits 143, 130 or 129. Each child gets TERM again every 0.1s (bash drops a signal that reaches a child before it has reset the parent's traps), KILL after 3s, and is never waited for (bash reaps it; a zombie left at exit goes to init), so cleanup never blocks for long. A `wait` there could block: when launchd's TERM to the group also ends the watchdog just as it interrupts the script's `wait` for the fetch, bash 3.2 and 5.2 can reap the watchdog without noting it, and a later `wait` for it lasts until the fetch exits, which no watchdog bounds any more. `ps` tells an exited child (a zombie) from a running one; when `ps` is missing, fails or prints nothing, only `kill -0` decides and the child counts as running, so it still gets TERM, then KILL after 3s. The watchdog also ends the `sleep` it is in, on TERM, INT or HUP. `fork/scripts/fetch-upstream-signal-stress.test.sh` signals the script inside its startup window 200 times per signal (`ORCA_FETCH_STRESS_RUNS`, `ORCA_FETCH_STRESS_BASH`) and checks each run exits within 5s with nothing left running. It repeats the cases with a `ps` shim that fails or prints nothing first in the script's PATH, and with a PATH that links every command of the full PATH except `ps` (`ORCA_FETCH_STRESS_NO_PS_RUNS`, default 20). A fetch that ignores TERM must be ended by the KILL after 3s: each such run takes 2.9–8s and leaves nothing (`ORCA_FETCH_STRESS_KILL_RUNS`, default 3). It also sends TERM, INT and HUP to the script's whole group while it waits for a running fetch, as launchd does, 100 times each (`ORCA_FETCH_STRESS_GROUP_RUNS`), each within 5s with nothing left. A missing bash, `ps`, git, perl or awk fails the test with a message and exit 2. The test's own checks use `ps` by absolute path, and a run still going after 35s is killed from outside and counted as a failure. Several runs of the stress and identity tests can share one checkout: each stress run tests its own copy of the script in its own temp dir and only finds and kills processes of that copy, that dir, its own process group and its own `sleep` helper (never by name or pattern); the identity test only kills pids and groups it recorded. Started from a non-interactive background job (`bash -c '… &'`), a test inherits SIGINT ignored, and under `nohup` SIGHUP (both with `nohup … &`), which bash cannot undo, so both tests first check (`fork/scripts/signal-test-preflight.sh`) that the bash under test can trap INT and HUP and otherwise rerun themselves once with both reset to the default by perl (works for bash 3.2 and 5.2), or exit 2 with a message instead of reporting timeouts. A signal that arrives while the fetch and the watchdog are being started, before their pids are known, is recorded and handled the same way as soon as both pids are set. An EXIT trap runs the same cleanup on every other exit, each step once. `run-linux-verify.sh` fetches the same way before `check-no-internal-refs.sh`.

## Home Mac: build, sign, publish

LaunchAgent `com.orca.fork.mac-auto-update` runs `~/Projects/orca-verify/bin/mac-auto-update.sh`, a copy outside the checkout. The installer refreshes that copy. The script also re-executes itself from a temp file before any git command, so `git reset --hard origin/develop` cannot rewrite the file that is running. After a run that published the updater, including a run whose dmg is still pending, it refreshes the installed copy with `cp` to `.next` and `mv`. A `skipped` run does not. A run that failed before the release was public leaves the previous copy in place.

That script fetches `origin/develop`. When that sha is not the last fully published sha, it resets a clean `develop` checkout to the remote tip (reflog keeps the previous tip), seeds the glibc 2.17 Node archive, and runs `fork/scripts/install-mac-release.sh --build-only`. Signing stays `Orca Local Signing`. It does not install the app. It does not download the zip or dmg back from the release.

`~/Projects/orca-verify/sync.env` must set `ORCA_BUILD_RELEASES=1` and `ORCA_PUBLISH_RELEASE=1`. `fork/scripts/publish-mac-release.sh` publishes a prerelease on `quzard/orca-fork`, tagged `v<version>` at the built commit. The release stays a draft until the updater files are on it, in this order: each mac zip, that zip's `.blockmap`, then `latest-mac.yml`. That yml lists only the zips. The draft is published as soon as those files are uploaded, and the dmg plus its `.blockmap` are uploaded to the same release afterwards. Installed apps can update while the dmg is still uploading. electron-updater's GitHub provider reads `latest-mac.yml` and requires every file named there to already be an asset; it then downloads the zip. Differential updates also need the zip `.blockmap`. The provider does not download the dmg. Linux SSH prebuilds are packed inside the app by the build and are not release assets. If a later dmg upload fails, the release stays published, `sync-status.json` uses `published-dmg-pending` for both `result` and `release`, and the next run uploads only the missing dmg files. It does not create a second release or a second copy of the zip. A finished release is `published`. Before publishing an existing release, the script may download the small `latest-mac.yml` already on it, and replaces that file when it names something that is not uploaded yet. The home Mac needs `gh` logged in with write access to `quzard/orca-fork`. Client Macs do not need `gh`. The app reads it anonymously with electron-updater's public GitHub provider, which tries `local-mac.yml` first and then `latest-mac.yml`. The script has no built-in proxy. If the home Mac needs one, set `ORCA_PROXY=<proxy url>` in `sync.env`; the script uses it for `http_proxy`, `https_proxy`, and `ALL_PROXY` (and the upper-case `HTTP_PROXY` / `HTTPS_PROXY`) unless `sync.env` sets those directly. Without either, it runs without a proxy. It always sets Node's `NODE_USE_ENV_PROXY=1`.

launchd does not load the login shell's `PATH`. The script and the LaunchAgent plist prepend `/opt/homebrew/bin`, `/usr/local/bin`, `~/.orbstack/bin`, and `/Applications/OrbStack.app/Contents/MacOS/xbin`. OrbStack's `docker` lives in that app `xbin` when `~/.orbstack/bin` is absent. `build-orcad-linux-prebuilds.sh` checks the same directories if `docker` is still missing. `sync.env` does not need a Docker `PATH` line. The LaunchAgent runs the copy in `~/Projects/orca-verify/bin`. Re-run `bash fork/scripts/install-mac-auto-update-agent.sh` after pulling a change to this script. A run that did not publish leaves the previous copy in place. A run that published the updater refreshes the copy even when the dmg is still pending.

`gh auth status` runs only after the "already published" check. A sha whose status is `published` does not contact `gh`. `published-dmg-pending` does contact `gh` and retries the dmg. If auth fails, `sync-status.json` keeps the previous `release` value and sets `ghAuth` to `failed` with the reason in `error`. It does not mark that sha `skipped`. When `dist/` still contains that sha (the local version suffix embeds the 12-character commit), the next successful auth publishes those files and does not build or sign again.

A background `codesign` under launchd can stop on a keychain prompt for the `Orca Local Signing` private key and never finish. After install, and before `--bootstrap`, run the installed script once from Terminal and click Always Allow. The build runs in its own process group. A `codesign` in that group that runs longer than `ORCA_CODESIGN_TIMEOUT_SECONDS` (default 600) causes the whole group to be killed, so electron-builder and node do not keep writing `dist/`. A denial (`errSecInternalComponent`, `errSecAuthFailed`, `errSecInteractionNotAllowed`, or "User interaction is not allowed") is recorded in `sync-status.json` instead of leaving the job hung. A lock file stops a second run from building while the first is alive.

Status file: `~/Projects/orca-verify/sync-status.json` (`sha`, `builtSha`, `version`, `result`, `startedAt`, `finishedAt`, `error`, `release`, `ghAuth`). `result` is `published`, `published-dmg-pending`, `up-to-date`, `built`, `skipped`, or `failed`. `published` means the zip, its blockmap, `latest-mac.yml`, and the dmg are all on the release. `published-dmg-pending` means the updater can already see the release and the dmg upload still needs another run. The build log is `~/Projects/orca-verify/mac-build.log`; each run truncates it.

The glibc 2.17 tarball is not downloaded from the unofficial Node host. Place the archive that `nodeRuntimeAsset('linux-x64-glibc217')` in `src/shared/node-runtime-pin.ts` names (today `node-v24.21.0-linux-x64-glibc-217.tar.gz`, with the sha256 listed there) in `~/Projects/orca-verify/node-runtime-cache/`, or set `ORCA_NODE_UNOFFICIAL_MIRROR` in `sync.env` to a URL or base that serves that exact archive. The script reads the name, version and hash from the pin, so a pin bump needs the new archive. It checks them first: the version must be `X.Y.Z`, the sha256 64 lowercase hex characters, and the archive exactly `node-v<version>-linux-x64-glibc-217.tar.gz`; otherwise the run stops with `glibc 2.17 Node pin has an invalid version`, `an invalid sha256` or `an unexpected archive name`. `fork/scripts/mac-auto-update-seed.test.sh` covers these cases, the cache hit and the mirror download. That directory is the default `ORCA_NODE_RUNTIME_CACHE_DIR`. It stays outside the checkout so `git clean` does not delete it. The Linux prebuild mounts it into the manylinux container at `/node-runtime-cache` and rewrites the pinned Node path. Leave the variable unset. Do not point it at `out/node-runtime-cache` inside the repo.

LaunchAgent `com.orca.fork.mac-auto-update` runs the script at login and every 30 minutes. It uses the Mac's local timezone only for the clock; the interval is not a 03:00 schedule. Codesign needs an unlocked login keychain, so the user stays logged in. Locking the screen is fine. Logging out skips the run.

```bash
mkdir -p ~/Projects/orca-verify/node-runtime-cache
# copy the glibc 2.17 archive into that directory
printf '%s\n' 'ORCA_BUILD_RELEASES=1' 'ORCA_PUBLISH_RELEASE=1' > ~/Projects/orca-verify/sync.env
# only if this Mac needs a proxy:
# echo 'ORCA_PROXY=<proxy url>' >> ~/Projects/orca-verify/sync.env
# gh auth status must succeed, with write access to quzard/orca-fork
bash fork/scripts/install-mac-auto-update-agent.sh
ORCA_REPO="$PWD" ~/Projects/orca-verify/bin/mac-auto-update.sh
# click Always Allow on the Orca Local Signing prompt, then:
bash fork/scripts/install-mac-auto-update-agent.sh --bootstrap
```

Run the installer from the checkout. The installed copy cannot infer the repo, so the manual run sets `ORCA_REPO`. Do that manual run before `--bootstrap`: `RunAtLoad` would otherwise show the keychain prompt under launchd, where it cannot be clicked.

An agent installed earlier still points its plist at `fork/scripts/mac-auto-update.sh` inside the checkout. That copy re-executes from a temp file, so `git reset` does not cut it off mid-run, but it is not the stable path. Re-run `bash fork/scripts/install-mac-auto-update-agent.sh`, run `ORCA_REPO="$PWD" ~/Projects/orca-verify/bin/mac-auto-update.sh` once and click Always Allow, then `bash fork/scripts/install-mac-auto-update-agent.sh --bootstrap`.

Remove the agent with `bash fork/scripts/uninstall-mac-auto-update-agent.sh`. Installing the plist does not load the agent until `--bootstrap`.

## Bridge release to the old repo

Apps installed before the move still poll the old fork repo. `fork/scripts/publish-bridge-release.sh <tag> [old-repo]` (default `quzard/orca`) copies an already published `quzard/orca-fork` prerelease there so those apps can update once to a build that reads `quzard/orca-fork`. It needs `gh` logged in with write access to the old repo, and run by hand; the LaunchAgent does not run it.

The script downloads every asset of `<tag>` from `quzard/orca-fork` into a temp dir and checks that the source is a published prerelease and that `latest-mac.yml` lists only zips that are present. It creates `<tag>` on the old repo as a draft prerelease targeting the old repo's default branch, with the notes "Bridge to quzard/orca-fork". It uploads each zip, each zip `.blockmap`, then `latest-mac.yml`, publishes the release with `gh release edit --draft=false`, and uploads the dmg files afterwards (`--no-dmg` skips them). Finally it checks that `<tag>` is the newest non-draft prerelease on the old repo and that the updater files are on it. A draft of the same tag left by an earlier failed run is filled in rather than created again. An already published tag stops the script. `--dry-run` runs the read-only checks and the download, and only prints the write commands. gh errors that look like they contain a token are replaced by a fixed message. `fork/scripts/publish-bridge-release.test.sh` runs it against a fake `gh`.

## In-app updates

Release checks read `quzard/orca-fork` anonymously through electron-updater's public GitHub provider (the releases atom feed and `releases/download` assets on github.com). There is no token setting or token file, `GH_TOKEN` / `GITHUB_TOKEN` are not read, and no `Authorization` header is sent. `allowPrerelease` is on, because every fork release is a prerelease and `/releases/latest` would 404. The public provider first asks for `local-mac.yml` (from the `-local.` prerelease tag) and falls back to `latest-mac.yml`. A fork build does not list upstream versions, pin a specific upstream tag, open `stablyai/orca` release notes, fetch the `onorca.dev` changelog or nudge, or download agent state rules from upstream releases. Unregistered (upstream) builds still use the public `stablyai/orca` feed.

On macOS the restart card waits until Squirrel has staged the download. If staging fails, the update card shows an error and the next check downloads again.

The app already installed on each Mac still requests `https://github.com/stablyai/orca/releases/latest/download` until one manual install of a build that contains this hook. After that, both Macs update from the published prerelease. `1.4.228` sorts above `1.4.228-local.<timestamp>.<sha>`, so an unhooked build can still be offered the upstream stable release. A later local timestamp sorts above an earlier one under the `semver` package electron-updater uses.

ShipIt checks the downloaded zip against the running app's designated requirement (`codesign -d -r-`). The same `Orca Local Signing` certificate on both Macs satisfies that check. This tree does not run that replacement. The end-to-end check is: install an older fork build that contains this hook, publish a newer prerelease, then confirm the notification, the download, the install, and the relaunch. If ShipIt rejects the zip, install the dmg from the same release by hand.

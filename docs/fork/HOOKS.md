# Fork hooks

These hooks are the only intentional edits to upstream files. Each hook is a registry in `src/shared/fork-hooks/`. Upstream code calls the registry; the fork registers behavior from `src/fork/`. Until a registration runs, every hook keeps upstream behavior: no extra await, no extra DOM, no extra menu row, no change to persisted values.

## Registration

| Entry                                | Called from                                                                                                                                                                                       | Registers                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/fork/register.ts`               | `src/main/index.ts` (before preflight), `src/renderer/src/main.tsx`                                                                                                                               | Fork build flag, skill source pin, host-directory sidebar mode, keeping a `sidebarGroupId` an older host omitted. | `src/fork/main/register-main.ts`     | `src/main/index.ts`, `startOrcad` in `src/main/orcad/orcad-entry.ts` (via `installForkOrcadHost`, which then installs the host adapters; the same import line also takes `resolveOrcadServeBind`) | Fork build flag, skill source pin, AI Vault service heap and scan policy (tool index and schema offset), deferred startup proxy, folder-workspace terminal resolver, imported worktree path, Cursor remote launch. `resolveOrcadServeBind` (`src/fork/main/orcad-serve-bind.ts`, re-exported here) is upstream's bind-host resolve plus terminal admission, one call only because `orcad-entry.ts` is at the line limit, not a fork feature. |
| `src/fork/main/register-electron.ts` | `src/main/index.ts` only                                                                                                                                                                          | Release feed, macOS file secret store, Computer Use permission helper argument. orcad never loads it, so orcad does not load Electron.                                                                                                                                                                                                                                                                                                       |
| `src/fork/register-renderer.tsx`     | `src/renderer/src/main.tsx`, right after `registerForkModules()`                                                                                                                                  | Sidebar chrome and drops, AI Vault slots, post-import handoff, composer seed, open-in launchers, port forward, terminal reconnect pulse, terminal file-link workspace setting, workspace-repository source control, en and zh overlays.                                                                                                                                                                                                      |

Built-in ids are refused by the registries, so a registration cannot replace Project, Status, PR, or None grouping, and cannot replace the Electron secret store unless `registerDesktopSecretStore` is called. Paired clients still validate `groupBy` with the upstream Zod enum: a desktop-only mode survives in the desktop profile store, and a phone that sees an unknown id keeps its previous mode.

## TypeScript projects

- The node project includes `src/fork/**/*.ts`. Fork code that imports the renderer is `.tsx`, so the node project never sees it.
- Main-process-only fork code lives under `src/fork/main/`. The web projects exclude `src/fork/main/**` and `src/fork/**/*.fork.test.ts` (node tests); renderer fork tests are `.fork.test.tsx`.
- `src/fork/tsconfig-boundaries.mjs` fails when a fork file imports a file outside a project that includes it. `pnpm typecheck` (`pnpm tc`) and `typecheck:ci` run it before tsc, and `src/fork/tsconfig-boundaries.fork.test.ts` runs it in the test suite.
- A fork test that uses the real SQLite runtime store must be listed in `NODE_RUNTIME_INCLUDE` (`config/scripts/vitest-node-runtime-files.mjs`). `findSqliteRuntimeTests()` also appends direct importers to `getNodeRuntimeInclude()`; the two fork SQLite tests stay on the explicit list because a dynamic import or shared helper is invisible to that scan.

## Release feed

`registerForkBuild` marks a fork build; `register.ts` and `main/register-main.ts` both call it. While it is set, nothing reads `stablyai/orca` or `onorca.dev`: version listing, pinned-tag resolution, the atom fetch (`src/main/updater-prerelease-feed.ts`), release-note URLs (`src/shared/release-channel.ts`, pointing at `quzard/orca-fork`), the changelog (`src/main/updater-changelog.ts`), the nudge (`src/main/updater-nudge.ts`), and the agent-state-rules download (bundled rules and a user override only). `src/main/updater/updater-setup.ts` does not set the public `stablyai/orca` URL.

Every source file that builds an upstream release or `onorca.dev/whats-new` URL is listed in `src/fork/upstream-release-sources.fork.test.ts` and must call `isForkBuild()`; an upstream sync that adds one fails the test. That scan checks only that the call is present; `src/fork/upstream-release-reads.fork.test.ts` and `src/fork/updater-fork-feed.fork.test.ts` cover the runtime behavior, and the latter drives the real updater and asserts no `stablyai` feed is pinned. `getReleaseDownloadUrl` throws in a fork build as a last guard.

`registerForkUpdateFeed` (from `src/fork/main/register-electron.ts`) makes `pinDefaultReleaseFeed` apply `forkGithubUpdateFeed()`: electron-updater's public GitHub provider for `quzard/orca-fork`, `private: false`, no `token`, so `GH_TOKEN` / `GITHUB_TOKEN` are never read and no `Authorization` header is sent. A fork build without the feed returns not-available before the `releases/latest/download` fallback. There is no token setting, file, or IPC.

`src/main/updater-fork-background.ts` binds `src/fork/main/fork-background-download.ts` (through `src/fork/main/fork-update-adapter.ts`) to the updater events; `registerAutoUpdaterHandlers` in `updater-events.ts` passes the adapter on the handler context. A downloaded version stays "staging" until `isMacInstallerReady()` (always ready off macOS); only then can the restart card show. A Squirrel `error` while staging clears the staging version and surfaces an `error` status. When `isMacStagingDeferredToInstall()` is true (supervised headless serve), a finished download counts as ready. Known limitation: if Squirrel neither finishes nor errors, the version stays staging and a manual check keeps showing 100% downloaded.

## Skill source commit

Upstream already exports `ORCA_CLI_COMMAND` in SSH terminals, so installed skills come from `https://github.com/stablyai/orca`, and `src/shared/agent-feature-install-commands.ts` matches upstream. A fork build's own commit is not on that repository, so skill install, skill update, and `orca skills` clone the upstream base recorded in `src/cli/skills-source-commit.ts`. `fork/scripts/sync-skills-source-commit.mjs` rewrites it after each sync: `git merge-base HEAD fork/base-upstream` (then `origin/fork/base-upstream`); without that ref, `git merge-base HEAD upstream/main` (then `origin/upstream/main`), never the upstream tip; with neither, the checked-in pin. The file lives under `src/cli` so `out/cli/**` unpacks it; production CLI source must not import `src/fork`. Upstream tests that assert the build-commit URL mock this registration; `src/fork/skills-source-commit.fork.test.ts` and `skills-source-commit-renderer.fork.test.tsx` assert the pin. Evidence for the SSH CLI path is in [skill-update-flow.md](skill-update-flow.md).

## Fork strings

Fork English lives in `src/fork/i18n/en.json` and Chinese in `src/fork/i18n/zh.json`; `src/fork/i18n/locale-overlay.ts` merges each into its language when that catalog loads, adding only missing keys. Upstream `en.json`, `en-runtime-required.json` and `zh.json` match upstream. Fork code translates through `forkTranslate` (`src/fork/i18n/fork-translate.tsx`), never `translate` directly, so upstream's extraction check, which matches `translate` and checks upstream `en.json`, never sees fork keys and `config/i18next.config.ts` stays upstream. No upstream file translates a fork key; `src/fork/i18n/fork-keys-catalog.fork.test.ts` checks that, that fork code never calls `translate` directly, and that every `forkTranslate` key has English and Chinese. A key is either a string literal or comes from a typed const list the test reads (`CONTEXT_MENU_LABEL_KEYS` in `src/fork/sidebar/context-menu-label-keys.ts`, `SSH_STATUS_KEYS` in `src/fork/ssh/ssh-status-keys.ts`); template-literal keys fail the test. Labels registered from node-safe code (`register-mode.ts`: the Host mode and the ungroup-only option) stay English there and get translated getters in the renderer (`src/fork/sidebar/mode-labels.tsx`); it also notifies the group-mode label version on i18n `languageChanged`, so the group-by menu relabels without another re-render.

## 修掉的问题

1. 暂存区里的改名：嵌套仓库的 `oldPath` 没加仓库前缀，fork 的 diff 方法也不收 `oldPath`，改名文件显示成整段新增。现在两边都带上，和上游一样只在暂存区用。
2. 嵌套仓库里的冲突文件走上游冲突流程：上游按根工作区跟踪冲突，下一次根状态里没有这条就把标签清掉，「标记已解决」还会在根仓库上执行。现在嵌套仓库的冲突条目按普通 diff 只读打开；根仓库的冲突仍走上游。
3. `git status` 读失败（`readError`）被丢掉，坏掉的嵌套仓库显示成干净的，「只显示有改动的」还会把它滤掉。现在带上错误，这一栏排前面、展开、写出原因，过滤时留着。
4. 分离 HEAD（子模块常见）的默认基线不进缓存，每次状态轮询都重跑一遍 `getBaseRefDefault`。现在和有分支的仓库一样按 HEAD 记五分钟。
5. 比较目标文件：合法 JSON 但不是这一版格式（`[]`、`version: 2`）会被当成空表覆盖。现在和坏 JSON 一样不覆盖。跨进程只靠「再读一次」缩小窗口，换成上游的文件事务锁之后，桌面和共用 userData 的 `orca serve` 同时写也不会丢。读改成异步，状态轮询不再在主进程里同步读文件。
6. 轮询：窗口不可见时照样每 4 秒跑一遍 git；切走再切回来，上一次比较到哪里丢了，所有仓库重新做分支比较；手动刷新之后每次重新显示面板都再强制刷新一次。现在窗口不可见就停，显示时立刻补一轮；一轮跑得慢就按耗时拉长间隔（最多 30 秒）；比较记录跨重启保留；手动刷新只强制一轮；内容没变的结果不触发重画。
7. 一轮轮询里状态请求超过 5 秒缓存时，每个仓库各自重扫一遍工作区。现在状态和 diff 只查成员，一分钟内的上一轮列表（包括超时截断的）都能用；查不到再按列表的 5 秒缓存判一次（同一个工作区最多 5 秒重扫一次，乱传路径也扫不起来），仍不在就拒绝。列出仓库仍是 5 秒缓存，超时的结果不当完整列表用。发现缓存里过期的条目在写入时清掉。
8. 远端调用没有显式超时：发现本身最多 15 秒，而远端调用默认也是 15 秒，扫描刚好超时时回不来 `timedOut`。现在列表 20 秒，其余 15 秒。
9. 能力探测：主机连不上被当成「主机太旧」，而且只在换工作区时再探，重连或升级之后开关一直灰着。现在分开提示「连不上」和「请更新主机」，面板开着时 15 秒再探一次。
10. 换工作区的第一帧仍用上一个工作区的范围，会先给新工作区发一次列表请求再撤掉。现在范围按工作区 id 同步算出来。范围表只记「工作区仓库」，切回当前仓库就删掉，表不再无限增长；写 localStorage 失败不再在点击里抛错。
11. 列出仓库失败时界面一直停在「正在查找仓库…」。现在显示失败原因。比较目标保存失败（主机拒绝、文件读不了）以前什么都不显示，现在输入框下面说明原因，草稿留着。基线不存在、没有共同祖先、比较出错时写出原因，不再只是没有领先落后。比较目标输入框有无障碍标签。
12. diff 标签按面板记下的仓库清单分流，面板没开时这份清单会一直旧下去。现在超过一分钟先重新发现；发现失败时有旧清单就按旧清单，路径落在嵌套仓库里仍不改拿根仓库的 diff。
13. 嵌套仓库的状态读取不再带根工作区的共享链接路径（那些路径是相对根的）。根仓库这一栏仍和上游 `git.status` 一样带上。

## 直连 SSH

上游已经没有在桌面进程里经 SSH 连接跑 git 的路子：#27215 删了 relay，#27477 让 `ssh:` 路由不带 provider、只抛 `SshHostNotServedError`，#27644 删了 SSH 的 git 和文件系统 provider。从 1.4.225 起每台 SSH 主机都在连接时部署或转换成 orcad，工作区行变成 `runtime:<环境>`，F047 本来就按 environment 目标把请求发到那台主机的 orcad。剩下的 `ssh:` 行是还没转换、或者被拒绝接管（unserved）的主机，上游自己的源代码管理面板在这些行上也读不了 git（提示重新连接）。要让它们能用，只能在 fork 里重新做一个 SSH git provider，和上游方向相反、量也大。所以保持灰掉，提示改成「这台 SSH 主机还没有由 Orca 服务端接管。重新连接后才能查看工作区仓库。」

## 暂存、取消暂存、提交

这一轮仍是只读。服务端已经顺手铺好了：嵌套仓库的目标可以原样交给上游的 `RuntimeGitStagingCommands` 和 `commitRuntimeGit`，加方法不用再动上游文件，旧主机用一个新的能力（例如 `fork.git.workspace-repositories.write.v1`）挡住即可。没有做的原因在界面：上游的提交不只是一条 `git commit`，还有按工作区保存的草稿、合并或变基进行中的处理、钩子失败后的恢复提示、进行中的 git 变更检测、AI 生成提交信息。在 fork 的列表里另做一套，要么少掉这些边界（出错时用户不知道仓库处于什么状态），要么复制一份上游提交流程、以后跟着漂移。需要在嵌套检出里提交时，把它当成自己的 Orca 工作区打开（`git worktree add` 的检出可以直接导入），用上游完整的面板。

## 手动验收

准备一个本机需求目录（自己是 git 仓库），下面放：`frontend/`（普通 clone）、`backend/`（`git worktree add` 出来的检出）、`.cache/`（带 `.git`，应跳过）、`node_modules/pkg/`（应跳过）、指向别处仓库的目录软链 `linked/`（应跳过），以及根 `.gitmodules` 里登记但没初始化的子模块。

1. 源代码管理选「工作区仓库」：根仓库在最上；有改动或领先的仓库排前面并展开，干净的收起；「其他」在最后、默认收起，里面是未初始化的子模块。标题显示分支、「N 项改动」「领先 X，落后 Y」。
2. 点 `backend` 里一个未暂存文件：打开的是 `backend` 自己的 diff，不是根仓库的整段新增。
3. 在 `frontend` 里 `git mv a.ts b.ts`：出现在「已暂存」，点开是改名 diff（左边是旧内容）。
4. 在 `frontend` 里造一个合并冲突：点冲突文件按普通 diff 打开，下一轮轮询后标签还在；根仓库「当前仓库」面板不出现冲突横幅。
5. 展开 `backend`，比较目标填 `origin/develop` 点「使用」：几秒内领先落后更新；重启 Orca 后仍是这个目标。填 `origin/nope`：这一栏写出「无法比较分支：…」。填 `-x`：输入框下面写出保存失败的原因，草稿还在。点「清除」回到默认（`origin/HEAD`）。
6. 把 `frontend/.git/index` 写坏：这一栏排到前面并展开，写出「读取状态失败：…」；打开「只显示有改动的」也不会被滤掉。修好后恢复正常。
7. 面板开着时把 Orca 窗口最小化：活动监视器里不再每几秒冒出 git 进程；恢复窗口立刻刷新一次。
8. 工作区 A 选「工作区仓库」、B 选「当前仓库」，来回切换：各自保持，切换瞬间不闪到另一种视图。
9. 打开一个嵌套仓库文件的 diff 标签，关掉源代码管理面板，过一分钟以上（或重启）再看这个标签：内容仍是嵌套仓库的 diff。
10. 托管 SSH（x86_64 Linux 服务器上的 orcad，桌面这一版部署的）：打开那台主机上的同样布局的工作区，开关在探测后可用，列表、状态、diff、比较目标都来自服务器。
11. 断网或断开 SSH 后打开 10 的面板：提示「连不上这台主机…」；恢复连接后约 15 秒内开关重新可用，不用切换工作区。
12. 主机上是没有这个能力的旧 orcad：开关灰掉，提示「请先更新这台主机…」，不发新方法。
13. 还没被 orcad 接管的 `ssh:` 行（unserved）：开关灰掉，提示重新连接这台主机。
